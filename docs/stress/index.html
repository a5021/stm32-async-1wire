Stress test report

DMA feed margin under memory-subsystem load - STM32F030x6

Measured 2026-11-05 at commit 1c6aaa87 on STM32F030x6 (STM32F030x6). Build 0_dma_pressure, pattern 00FFAA550FF03CC3, 64 slots per frame, 100 frames per cell, 512 halfwords per DMA burst. Each cell carries the SHA-256 of its image in results.json

Summary

The wire stayed correct under every tested load.
  • Every level and clock is clean at the 1 us floor (a 2 us window).
  • cndtr_late is 0, no DMA error was latched, and no channel-stop timeout occurred in any cell.
  • Load activity: at 48 MHz channel 1 restarted 8300 times; at 8 MHz channel 1 restarted 1400 times (level 4; level 5 adds the CPU hammer).
  • The 5 us guard is a 6 us window, 3.0x the measured 2 us floor. The library and DMA priority stay unchanged.
  • Search ROM under the same loads returned the same 7 devices and checksum in all 24 cells.
  • A delayed feed (16 us) and capture (200 us) both fail the checks, so the harness catches a late transfer.

This test checks whether memory load can delay the CCR3 feed DMA past its slot deadline. On this bench it cannot: the transfer always landed before the update, even when the load halved the CPU's SRAM throughput.

What can go wrong

Each write slot is one TIM1 period. At CC2, DMA1 channel 3 is asked for the next CCR3 value. The update event starts the next slot. The transfer must land between those events: guard + 1 microseconds (the counter runs from 0 to ARR inclusive).

Late transferWhat the wire shows
A transfer past the updatethe slot repeats its previous bit; the decoded pattern changes and a frame can lose the final release.
A transfer inside the next low pulsethe pulse stretches or a second edge appears; the slot no longer matches a '1' or a '0' width.
A transfer never servicedCNDTR stays non-zero at completion and the line can be parked low - complete starvation.

On DMA-fed paths OC3PE is off. A late CCR3 write takes effect immediately, so a failure can appear inside the current slot, not only at the next one.

Rig and method

examples/0_dma_pressure sends a fixed 8-byte pattern (64 slots plus the release) back to back while a selectable load runs beside the bus. The bench is STM32F030x6; D0 is the 1-Wire line on PA10. The capture runs at 4.0 MS/s. The harness flashes the firmware halted and resets it, so only the intended run is measured.

The first slot is armed by a register write, not the feed DMA. Its width includes the CPU gap between enabling OC3 and starting the timer (about 1 us at 48 MHz, 7 us at 8 MHz), so the check skips that slot's width and the first period of each frame. Guard 0 is not an operating point: CC2 then coincides with the update, and the release write adds a spurious end-of-frame pulse.

Load placement and DMA priority

On a classic DMA controller or an F4 DMA stream, equal software priority is broken by the lower channel/stream number. The historical load sits on the low numbers (F0 channels 2/1, F4 streams 0/1), so it outranks the feed; the "high" runs move the same burst to the higher numbers, where the feed wins. GPDMA has no such tie: CCR.PRIO selects the class, so the H5 "high" run keeps channels 0/1 and raises the load to PRIO 3 against the feed's PRIO 0. A part that is clean in both rows has spare bandwidth; a part that is clean only with the load below the feed is sensitive to arbitration order.

Interpretation

  • No wire-visible slip at the 2 us floor on either clock, under any load.
  • cndtr_late = 0 everywhere: every feed transfer was serviced before completion, including the final release.
  • Load activity: channel 1 restarted thousands of times per run (see the table), and the CPU hammer ran too. The feed still met the 2 us floor.
  • The 6 us guard is a 2 us window, and 2 us is the smallest guard that stayed clean. The wire stayed correct there, so this part does not need a larger default and the library keeps its DMA priority.

Caveats

  • Equal priority only. Every load channel uses the default DMA priority. An application channel with PL > 0 is a different case and is not covered. The equal-priority tie-break is covered: the load sits on low channel/stream numbers, so it outranks the feed; the priority section shows the same load on high numbers.
  • One rig, several benches. Each part used the same firmware and loader. On parts with fewer channels the high-placement load uses the next free number (the F030F4 has no channel 6, so it uses 4). Wiring and marker pins differ per board.
  • One part, one bench, write-only. The pattern is not a 1-Wire transaction and the devices are never addressed, so this measures master timing, not a protocol exchange.
  • Timer floor. The 1 us timer cannot resolve a guard below 1. The report says "a 2 us window was enough", not "the latency is exactly 1 us".
