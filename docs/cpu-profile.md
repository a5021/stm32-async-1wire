# CPU cost of the non-blocking 1-Wire driver

The 1-Wire waveform is generated by TIM1 and DMA; the CPU does not bit-bang the
bus. This page measures what the CPU actually does inside the driver: the
state-machine branch that advances a search or a measurement when a hardware
operation completes. Idle `*_poll()` calls and application callbacks are
excluded.

## What is measured

`example/2_device_search` runs a Search ROM pass at startup and then measures
one DS18B20 per cycle with Match ROM. The profiler uses `SysTick->VAL` around
the driver's real-work branch:

- `ds18b20_poll()`: the `onewire_bus_done() == 1` branch that advances the
  measurement state machine;
- `onewire_search_poll()`: the equivalent branch for the Search ROM engine.

The application callbacks (`ds18b20_complete()` and the search ROM sink) are
paused out, because they format UART output rather than process the bus. The
measured intervals include reset/command setup, starting the conversion wait,
the scratchpad read, decoding and CRC.

A separate profiler calibration measures the hook itself; the reported cycles
already have that overhead subtracted (18 cycles/event on the H503, 10 on the
F030).

## Setup

| | H503 | F030 |
|---|---|---|
| Part | STM32H503xx | STM32F030x6 |
| Clock | 250 MHz (8 MHz HSE + PLL) | 8 MHz (HSI) |
| Core | Cortex-M33 | Cortex-M0 |
| Devices | 7 × DS18B20, parasite-powered bus | 7 × DS18B20, parasite-powered bus |
| Build | `-Os -flto`, `OW_PARASITE_POWER=1` | `-Os -flto`, `OW_PARASITE_POWER=1` |
| Run | 300 s, 52 measurement cycles | 300 s, 52 measurement cycles |
| Measurement phase | 790 ms (750 ms conversion wait included) | 791 ms |
| Full cycle with 5 s pause | 5.79 s | 5.79 s |
| Search phase | 274 ms | 293 ms |

The measurement phase is the interval from `ds18b20_start_measure()` to
`ds18b20_complete()`. The 5 s application pause after the result is not part of
it.

## Results

| Metric | H503 @ 250 MHz | F030 @ 8 MHz |
|---|---:|---:|
| One measurement: work cycles | 8,727 | 6,821 |
| One measurement: work time | 34.9 µs | 852.6 µs |
| One measurement: work events | 8 | 8 |
| One measurement: cycles/event | 1,090.9 (4.36 µs) | 852.6 (106.6 µs) |
| One measurement: worst event | 3,390 (13.56 µs) | 2,809 (351.1 µs) |
| One measurement: share of active phase | 0.0044% | 0.108% |
| One measurement: share of full cycle | 0.00060% | 0.0147% |
| Search ROM: work cycles | 219,159 | 134,100 |
| Search ROM: work time | 0.877 ms | 16.76 ms |
| Search ROM: work events | 543 | 543 |
| Search ROM: cycles/event | 403.6 (1.61 µs) | 247.0 (30.9 µs) |
| Search ROM: worst event | 1,686 (6.74 µs) | 1,114 (139.3 µs) |
| Search ROM: share of active phase | 0.32% | 5.72% |

## What the numbers mean

- The driver's real work is small. On the H503 one measurement costs 8,727
  cycles, or 34.9 µs; on the F030 the same sequence costs 6,821 cycles, or
  852.6 µs at 8 MHz.
- The F030 executes fewer cycles for the same sequence, but its clock is
  31.25× slower, so the wall time is about 31× longer.
- The measurement touches the driver in eight short work segments: reset and
  command setup, the conversion-wait start, the second reset, the scratchpad
  read, decoding and CRC, and the final state updates. The driver does not
  touch the bus between those segments; it only polls.
- Search ROM is more work because it has 543 state-machine events across the
  seven-device walk. It costs 0.877 ms on the H503 and 16.76 ms on the F030.
- The worst single event matters for latency: 13.6 µs on the H503 and 351 µs
  on the F030. A 351 µs step is the longest interval during which the F030
  main loop cannot do other work.

## What is not included

- **Idle polling.** An earlier H503 run that wrapped the whole
  `ds18b20_poll()` call measured 11.2% of the active phase. That is the main
  loop's polling occupancy, not driver work, and it is deliberately kept out
  of the table above. The two numbers answer different questions.
- The 750 ms conversion wait itself. The driver starts the wait and handles
  its completion; the elapsed wait is not CPU time.
- UART output and the application callbacks (`ds18b20_complete()` and the
  search ROM sink).
- Interrupts or other RTOS tasks.

## Limits

- One example, one seven-sensor parasite-powered bench, one `-Os -flto` build.
- A "work event" is a state-machine transition, not a full instruction-level
  profile. The cycles are measured with `SysTick->VAL`, which has a 1 ms
  period; every event is far shorter than that.
- The H503 and F030 use different cores and clocks. Compare cycles when
  comparing code cost, and microseconds when comparing wall time.
- The run is stable: the H503 measurement count was identical in every sample,
  and the F030 varied by only a few cycles. The table reports the measured
  average; the raw summaries carry the min/max values.

## Reproduce

The `cpu_profile.py` script builds, flashes, reads the UART for the requested
window and prints the summary. `--port` depends on the bench.

H503 at 250 MHz:

```bash
python tests/hil/cpu_profile.py --app 2_device_search \
  --mcu STM32H503xx --sysclk 250 --hse 8 --seconds 300 --port COM5
```

F030 at 8 MHz:

```bash
python tests/hil/cpu_profile.py --app 2_device_search \
  --mcu STM32F030x6 --sysclk 8 --hse 0 --seconds 300 --port COM5
```

The profiler is opt-in: the build adds `-DAPP_PROFILE=1 -DOW_PROFILE=1`.
Without those defines the hooks compile to nothing and the driver is unchanged.

Raw summaries: [H503, 250 MHz](cpu-profile/h503-250.json) and
[F030, 8 MHz](cpu-profile/f030-8.json).
