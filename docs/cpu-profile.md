# CPU cost of the non-blocking 1-Wire driver

The 1-Wire waveform is generated by TIM1 and DMA; the CPU does not bit-bang the
bus. This page separates three costs:

- **useful work** — the driver branch that advances a search or measurement
  after a hardware operation completes;
- **empty poll** — a public call that finds no completed operation and returns;
- **public poll** — the whole `ds18b20_poll()` / `onewire_search_poll()` call,
  which is useful work plus empty calls plus the application callback.

The application callback is UART formatting, not bus processing. It is reported
separately so the library cost is not mixed with the application cost.

## What is measured

`examples/2_device_search` runs a Search ROM pass at startup and then measures
one DS18B20 per cycle with Match ROM. Three counters are used:

- the work counter wraps only the `onewire_bus_done() == 1` branch in
  `ds18b20_poll()` and `onewire_search_poll()`;
- the poll counter wraps the complete public call;
- the empty counter times the calls that leave the work-event count unchanged.

A free-running hardware counter replaces `SysTick->VAL`: `DWT->CYCCNT` on the
Cortex-M33 H503 and `TIM14` on the Cortex-M0 F030. Both are read as an unsigned
difference; the F030's 16-bit counter wraps every 8.19 ms, far above the 0.902 ms
worst interval measured here. A sample in the upper half of the range is counted
as an overflow and rejected.

A calibration loop measures the hook itself; the reported cycles already have
that overhead subtracted (1 cycle/event on the H503, 4 on the F030). The
profiler's own bookkeeping sits outside the timed call, so it does not inflate
the per-call numbers.

## Where the active-phase CPU goes

Measurement phase:

| Component | H503 | F030 |
|---|---:|---:|
| Useful driver work | 0.0043% | 0.1088% |
| Empty poll (library) | 11.7208% | 15.8422% |
| Callback (application) | 0.0024% | 0.0549% |
| Other application loop | 88.2725% | 83.9941% |
| Total CPU busy | 100.0000% | 100.0000% |

Search phase:

| Component | H503 | F030 |
|---|---:|---:|
| Useful driver work | 0.3512% | 5.7222% |
| Empty poll (library) | 17.1959% | 13.7518% |
| Callback (application) | 0.1215% | 2.6378% |
| Other application loop | 82.3314% | 77.8882% |
| Total CPU busy | 100.0000% | 100.0000% |

The rows are exclusive. Empty poll is timed directly: it is the set of public
calls that leave the work-event count unchanged. The callback is what remains
of the public poll after useful work and empty calls are subtracted, and the
other-loop row is the remainder of the active phase. The last row is computed
as the complement of the displayed values, so each column sums to exactly
100.0000%; the unrounded numbers are in the linked JSON.

The example busy-polls, so the CPU is fully occupied during the active phase;
the other-loop row is the main loop (`app_millis()`, `uart_poll_tx()`,
branches), not idle sleep.

## How to read the percentages

The integration-relevant number is the cost of a poll that finds nothing:

- H503: 41 cycles, about 164 ns per empty call;
- F030: 33 cycles, about 4.1 µs per empty call.

That is the library's price for one pass through the public interface. The
callback is a separate, much smaller item for one measurement (0.0024% / 0.0549%
of the active phase); on the F030 the Search ROM sink is more visible at 2.64%
of the search phase because it formats seven ROMs once.

The percentages are a snapshot of the instrumented loop, not a universal CPU
load:

| Quantity | Workload-dependent? |
|---|---|
| Useful work per transaction | No, for a fixed operation mix and configuration |
| Cost of one empty call | No, for this build |
| Empty calls per transaction | Yes; it is the loop speed |
| Callback per completion | No, for this output format |
| Share of the active phase | Yes; the denominator includes empty polling and the app loop |
| Total CPU busy | Yes; 100% here because the example busy-polls |

The profiler adds bookkeeping after each timed call, which slows the polling
loop; the empty-call share above is therefore slightly lower than in the shipped
build, while the per-call cost and the useful-work cost are not affected. For a
fixed operation mix and configuration, useful-work time per transaction is
approximately constant: 34.1 µs per measurement on the H503 and 861.0 µs on the
F030. It changes with the operation itself, the resolution, parasite power, bus
length and the number of devices in a search, so it is not a universal
characteristic of the driver. With continuous polling and a sufficiently high
transaction rate, useful 1-Wire processing can occupy a substantial fraction of
CPU time. The percentage depends on the operation mix and on how much time is
spent waiting for hardware operations, so the small percentages above are not a
ceiling.

## Latency

Average load is not enough for a non-blocking driver; the longest single step
matters when other tasks share the CPU.

| Metric | H503 @ 250 MHz | F030 @ 8 MHz |
|---|---:|---:|
| Worst measurement work event | 12.44 µs | 357.1 µs |
| Worst measurement empty poll | 0.16 µs | 4.62 µs |
| Worst measurement public poll | 40.85 µs | 902.1 µs |
| Worst search work event | 6.92 µs | 139.6 µs |
| Worst search empty poll | 0.27 µs | 4.25 µs |
| Worst search public poll | 20.97 µs | 419.5 µs |

On the F030 the longest measured driver step is 357 µs and the longest public
poll is almost 900 µs. During that step the main loop cannot execute other code;
this is a measured driver/poll bound, not necessarily the absolute application
latency bound, which other code can also set.

## Blocking reference

The numbers above describe a non-blocking build. For comparison, a bit-bang
driver that busy-waits through the same transaction at standard speed would hold
the CPU for:

| Operation | CPU time |
|---|---:|
| 2 reset pulses (480 µs low + 480 µs recovery) | 1.9 ms |
| 232 slots × 61 µs (Match ROM ×2, Read Scratchpad) | 14.2 ms |
| 12-bit conversion wait, blocking | 750 ms |
| Total per measurement | ~766 ms |

This is an analytical estimate from the published 1-Wire timing, not a
measurement on this bench; decoding and CRC are omitted because they are small.
The non-blocking driver spends 92.6 ms (H503) or 126.6 ms (F030) inside `poll()`
during the active phase, and the 750 ms conversion wait costs no CPU at all.
That contrast, not the small useful-work share, is the practical meaning of
"non-blocking".

## Low-power builds

These are busy-poll builds. With `OW_LOW_POWER=1` the driver sleeps in `__WFE()`
during long hardware stages, so the application calls `poll()` roughly once per
completion event (8 per measurement) instead of hundreds of thousands of times,
and the core is asleep between them. That build is not profiled here; its energy
is set by the number of wake-ups and the sleep current, not by the busy-poll
percentages above.

## What is not included

- The 750 ms conversion wait itself. The driver starts the wait and handles its
  completion; the elapsed wait is not CPU time.
- The application loop outside the public poll calls. It is the "other
  application loop" residual in the breakdown, not separately instrumented.
- Interrupts. These examples install no interrupt handlers: SysTick is polled
  and the driver's UIE is only a WFE wake-up event, never an ISR.

## Limits

- `DWT->CYCCNT` and `TIM14` count elapsed hardware ticks, not retired
  instructions. The F030 counter is 16 bits and wraps every 8.19 ms; the worst
  interval measured is 0.902 ms, and no overflow was seen in either run.
- One example, one seven-sensor parasite-powered bench, one `-Os -flto` build.
- A "work event" is a state-machine segment, not a full instruction-level
  profile.
- The H503 and F030 use different cores, clock rates and peripheral backends.
  Compare cycles when comparing code cost, and microseconds when comparing wall
  time, but do not read cycles per poll call as a cross-platform efficiency
  ranking.
- The percentages are workload-dependent; the absolute work per transaction is
  the portable number.

## Reproduce

The `cpu_profile.py` script builds, flashes, reads the UART for the requested
window and prints the work, empty-call and poll summaries. `--port` depends on
the bench.

H503 at 250 MHz:

```bash
python tests/hil/cpu_profile.py --app 2_device_search \
  --mcu STM32H503xx --sysclk 250 --hse 8 --seconds 300 --port COM5
```

F030 at 8 MHz:

```bash
python tests/hil/cpu_profile.py --app 2_device_search \
  --mcu STM32F030x6 --sysclk 8 --hse 0 --seconds 300 --port COM5
```

The profiler is opt-in: the build adds `-DAPP_PROFILE=1 -DOW_PROFILE=1`.
Without those defines the hooks compile to nothing and the driver is unchanged.

Raw summaries: [H503, 250 MHz](cpu-profile/h503-250.json) and
[F030, 8 MHz](cpu-profile/f030-8.json).
