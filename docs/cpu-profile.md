# CPU cost of the non-blocking 1-Wire driver

The 1-Wire waveform is generated by TIM1 and DMA; the CPU does not bit-bang the
bus. This page separates two different costs:

- **useful work** — the driver branch that advances a search or measurement
  after a hardware operation completes;
- **public poll** — the whole `ds18b20_poll()` / `onewire_search_poll()` call,
  including the calls that find nothing to do and the application callback that
  runs inside the completion.

The difference between the two is the polling overhead. The application callback
is UART formatting, not bus processing, so the "polling" rows include it; the
useful-work rows do not.

## What is measured

`examples/2_device_search` runs a Search ROM pass at startup and then measures
one DS18B20 per cycle with Match ROM. Two `SysTick->VAL` counters are used:

- the work counter wraps only the `onewire_bus_done() == 1` branch in
  `ds18b20_poll()` and `onewire_search_poll()`;
- the poll counter wraps the complete public call.

The application callbacks (`ds18b20_complete()` and the search ROM sink) are
paused out of the work counter. The work intervals include reset/command setup,
starting the conversion wait, the scratchpad read, decoding and CRC.

A calibration loop measures the hook itself; the reported cycles already have
that overhead subtracted (19 cycles/event on the H503, 9 on the F030).

## Setup

| | H503 | F030 |
|---|---|---|
| Part | STM32H503xx | STM32F030x6 |
| Clock | 250 MHz (8 MHz HSE + PLL) | 8 MHz (HSI) |
| Core | Cortex-M33 | Cortex-M0 |
| Devices | 7 × DS18B20, parasite-powered bus | 7 × DS18B20, parasite-powered bus |
| Build | `-Os -flto`, `OW_PARASITE_POWER=1` | `-Os -flto`, `OW_PARASITE_POWER=1` |
| Run | 300 s, 52 measurement cycles | 300 s, 52 measurement cycles |
| Measurement phase | 790 ms (750 ms conversion wait included) | 791 ms |
| Full cycle with 5 s pause | 5.79 s | 5.79 s |
| Search phase | 274 ms | 294 ms |

The measurement phase is the interval from `ds18b20_start_measure()` to
`ds18b20_complete()`. The 5 s application pause after the result is not part of
it.

## Where the active-phase CPU goes

| Component | H503 | F030 |
|---|---:|---:|
| Useful driver work | 0.0043% | 0.108% |
| Idle poll + callback | 15.11% | 23.24% |
| Other application loop | 84.89% | 76.65% |
| Total CPU busy | 100% | 100% |

The example busy-polls, so the CPU is fully occupied during the active phase.
The last row is the remainder of the main loop (`app_millis()`,
`uart_poll_tx()`, branches), not idle sleep.

## How to read the percentages

The percentages are a snapshot of this example, not a universal CPU load:

| Quantity | Workload-dependent? |
|---|---|
| Useful work per transaction | No, for this operation mix |
| Polling + callback overhead | Yes; it fills the free time |
| Share of the active phase | Yes; the denominator includes idle polling and the app loop |
| Total CPU busy | Yes; 100% here because the example busy-polls |

The useful-work time is the invariant per transaction: 34.3 µs per
measurement on the H503 and 853.6 µs on the F030. If the application gives the
driver more transactions, the useful-work share rises because the extra work
replaces idle polling; the per-transaction cost stays the same. In the limit of
a saturated bus with no other work, the CPU is busy with 1-Wire processing
almost 100%; the small percentages above are not a ceiling.

## Latency

Average load is not enough for a non-blocking driver; the longest single step
matters when other tasks share the CPU.

| Metric | H503 @ 250 MHz | F030 @ 8 MHz |
|---|---:|---:|
| Worst measurement work event | 13.58 µs | 351.3 µs |
| Worst measurement public poll | 41.2 µs | 894 µs |
| Worst search work event | 6.76 µs | 139.4 µs |
| Worst search public poll | 20.6 µs | 417.1 µs |

On the F030 a single measurement work event can keep the main loop busy for
351 µs, and a public poll for almost 900 µs. That is the number to check when
another task has a latency budget; the average CPU share says nothing about it.

## What is not included

- The work counter excludes idle polls and the application callbacks. The
  public poll counter includes them, so the polling rows are polling plus
  callback overhead.
- The 750 ms conversion wait itself. The driver starts the wait and handles its
  completion; the elapsed wait is not CPU time.
- The application loop outside the public poll calls. It is the "other
  application loop" residual in the breakdown, not separately instrumented.
- Interrupts or other RTOS tasks. These examples install no ISR; if one fires
  inside a measured interval, its time is included by `SysTick`.

## Limits

- `SysTick->VAL` counts elapsed core-clock ticks. In the absence of interrupts
  this is the code's execution time in cycles; with an ISR inside the interval,
  the ISR time is included too. It is not a retired-instruction count.
- One example, one seven-sensor parasite-powered bench, one `-Os -flto` build.
- A "work event" is a state-machine segment, not a full instruction-level
  profile. The cycles are measured with `SysTick->VAL`, whose period is 1 ms;
  every event is far shorter than that.
- The H503 and F030 use different cores and clocks. Compare cycles when
  comparing code cost, and microseconds when comparing wall time.
- The percentages are workload-dependent; the absolute work per transaction is
  the portable number.

## Reproduce

The `cpu_profile.py` script builds, flashes, reads the UART for the requested
window and prints both work and poll summaries. `--port` depends on the bench.

H503 at 250 MHz:

```bash
python tests/hil/cpu_profile.py --app 2_device_search \
  --mcu STM32H503xx --sysclk 250 --hse 8 --seconds 300 --port COM5
```

F030 at 8 MHz:

```bash
python tests/hil/cpu_profile.py --app 2_device_search \
  --mcu STM32F030x6 --sysclk 8 --hse 0 --seconds 300 --port COM5
```

The profiler is opt-in: the build adds `-DAPP_PROFILE=1 -DOW_PROFILE=1`.
Without those defines the hooks compile to nothing and the driver is unchanged.

Raw summaries: [H503, 250 MHz](cpu-profile/h503-250.json) and
[F030, 8 MHz](cpu-profile/f030-8.json).
